# X301-v1 – normative rohe XDH-Funktion

## 1. Status und Geltungsbereich

> **TECHNICALLY SPECIFIED, NOT PRODUCTION AUDITED.** Dieses Dokument definiert
> eine bytegenaue rohe Diffie-Hellman-Funktion auf dem Montgomery-Modell von
> ED301-v1. Es definiert weder eine KDF noch einen authentisierten Handshake
> und bescheinigt keiner Implementierung Seitenkanalresistenz.

`X301-v1` ist das ED301-Gegenstück zur Funktionsschicht von X25519 und X448:
Ein geheimer 38-Byte-Eingang und eine kanonische 38-Byte-u-Koordinate werden
auf eine neue 38-Byte-u-Koordinate abgebildet. Die Schleifenform der Leiter
folgt [RFC 7748](https://www.rfc-editor.org/rfc/rfc7748.html); Feld,
Konstanten, strikte u-Dekodierung, Scalar-Clamping und Fehlerregeln sind
eigenständig und ausschließlich in diesem Dokument festgelegt.

Die großgeschriebenen Wörter **MUSS**, **DARF NICHT**, **SOLLTE** und **DARF**
bezeichnen normative Anforderungen. `FAIL` bezeichnet einen Fehler ohne
Ausgabebytes.

Normative lokale Grundlagen sind der
[Parametersatz](../parameter/ed301-v1.json) und die
[ED301-v1-Kurvenspezifikation](ED301-v1.md). Der
[Kurvenbericht](../berichte/KURVENBERICHT_ED301.md) dokumentiert die
mathematischen Nachweise. Bei einer Abweichung zwischen diesen fest
versionsgebundenen Quellen DARF eine Implementierung nicht raten; das Paket
ist dann als inkonsistent zurückzuweisen.

## 2. Klare Verfahrensgrenzen

Dieses Dokument definiert:

- die geheime 38-Byte-Eingabe und ihre deterministische Clamp-Regel,
- eine strikte kanonische 38-Byte-u-Kodierung,
- die feste Basis-u-Koordinate,
- die 301-Runden-Montgomery-Leiter,
- `KeyGen`, `Public`, `Shared` und die gemeinsame Kernfunktion,
- alle Fehlerfälle der rohen Funktion.

Dieses Dokument definiert ausdrücklich nicht:

- eine KDF oder die Verwendung der Rohausgabe als Schlüssel,
- Nachrichtenformate, Rollen, Transkript- oder Channel-Binding,
- Authentisierung, Schlüsselbestätigung oder Identitätsprüfung,
- Ephemeral-/Static-Handshakes, Forward Secrecy oder Wiederverwendungspolitik,
- ein Signaturverfahren; hierfür existiert das getrennte `Ed301-Sig-v1`,
- ein tolerantes RFC-7748-Decoding fremder oder nichtkanonischer u-Werte.

Ein Protokoll darf daher nicht allein wegen eines erfolgreichen
`Shared`-Aufrufs behaupten, ein sicherer oder authentisierter Kanal sei
etabliert.

## 3. Feste mathematische Parameter

Alle Operationen der Leiter erfolgen in `F_p`:

```text
p = 2^301 - 2^99 + 947
  = 4074071952668972172536891376818756322102936787331872501272280264883462485411972664015193011

FIELD_BYTES  = 38
LADDER_BITS  = 301
```

Das Montgomery-Modell lautet

```text
M: B*v^2 = u^3 + A*u^2 + u

A = 1337125101468798294423667083008487580371440947467333579746761624815927501631542793281919359

B = 2102386304867639485174889802292078795702081870378430469358638547115457185184343208357597462
```

Die normative Leiterkonstante verwendet ausschließlich die Minus-Konvention:

```text
A24_minus = (A-2)/4 mod p
          = 1352799263534442616740139614956810975618594433699801520254760472424847496760878864324278092
          = 0xaa029362ba3137bab9f5cdc1fc83a5ea81722d2225515ed71ca8cd44f2f09f485440646b74c
```

Sie gehört zur Verdopplungsformel

```text
z2 = E * (AA + A24_minus*E).
```

`(A+2)/4` DARF in dieser Leiter nicht verwendet werden.

Hauptkurve und expliziter quadratischer Twist besitzen die bewiesenen
Ordnungen

```text
N = 4*q
  = 4074071952668972172536891376818756322102936789371269161834491587034136893877719336157337612

q = 1018517988167243043134222844204689080525734197342817290458622896758534223469429834039334403

N_t = 4*q_t
    = 4074071952668972172536891376818756322102936785292475840710068942732788076946225991873048412

q_t = 1018517988167243043134222844204689080525734196323118960177517235683197019236556497968262103
```

`q` und `q_t` sind ungerade Primzahlen, beide Gesamtgruppen sind zyklisch,
und beide Cofaktoren sind exakt `4`. Der hier gemeinte Twist ist das in
ED301-v1 festgelegte Modell mit dem quadratischen Nichtrest `z=2`; es wird
nicht durch eine implizite oder implementierungsabhängige Twistwahl ersetzt.

## 4. Byte- und Integerfunktionen

Bytefolgen werden mit Index `0` beginnend notiert. Bitposition `0` ist das
niederwertigste Bit von Byte `0`.

Für `X = X[0]...X[n-1]` gilt

```text
OS2IP_LE(X) = Summe X[i]*256^i für i=0..n-1.
```

`I2OSP_LE38(x)` ist die eindeutige 38-Byte-Little-Endian-Darstellung eines
Integers `0 <= x < 2^304`. Ein außerhalb dieses Bereichs liegender Wert führt
zu `FAIL`.

`AllZero(X)` ist genau dann wahr, wenn jedes Byte von `X` null ist. Eine
produktive Implementierung MUSS diese Prüfung ohne datenabhängigen frühen
Abbruch ausführen.

## 5. Strikte kanonische u-Kodierung

### 5.1 Dekodierung

```text
function DecodeU(encoded):
    if encoded ist keine Bytefolge: return FAIL
    if len(encoded) != 38: return FAIL
    if (encoded[37] AND 0xe0) != 0: return FAIL
    u = OS2IP_LE(encoded)
    if u >= p: return FAIL
    return u
```

Damit tragen Bits `0..300` den Feldwert und Bits `301..303` sind zwingend
null. Insbesondere gilt:

- Das oberste Byte wird **nicht** tolerant maskiert.
- Werte `u >= p` werden **nicht** modulo `p` reduziert.
- Alternative Kodierungen desselben Feldelements werden nicht akzeptiert.

Diese Striktheit ist eine bewusste Abweichung von den toleranten
Eingaberegeln, die RFC 7748 für X25519-Interoperabilität verlangt.

### 5.2 Kodierung

```text
function EncodeU(u):
    if u kein Integer oder u < 0 oder u >= p: return FAIL
    out = I2OSP_LE38(u)
    assert (out[37] AND 0xe0) == 0
    return out
```

Die feste Basis-u-Koordinate ist die Montgomery-Abbildung des normativen
ED301-Basispunkts `G` exakter Ordnung `q`:

```text
BASE_U =
1067917942141295978366266158278333061632895636270240461974100298644709548352069314007836251

BASE_U_ENCODED =
5ba6f0f4ccc6ff5f018a2496fe165eb7d1893949fe3d05f79c12d2bd99952cd42d2ae9546308
```

`BASE_U_ENCODED` ist exakt 38 Byte little-endian.

## 6. Geheime Eingabe und Clamping

### 6.1 Normative Regel

Der geheime Eingang ist eine Bytefolge von **exakt 38 Byte**. Er wird nicht
zuerst als kanonischer Integer geprüft. Stattdessen wird eine Kopie wie folgt
geclampt:

```text
function DecodeScalar(secret):
    if secret ist keine Bytefolge: return FAIL
    if len(secret) != 38: return FAIL

    k_bytes = copy(secret)
    k_bytes[0]  = k_bytes[0] AND 0xfc
    k_bytes[37] = (k_bytes[37] AND 0x0f) OR 0x10
    k = OS2IP_LE(k_bytes)

    if k == N_t: return FAIL
    return k
```

Die Masken bewirken gleichzeitig:

- globale Bits `0` und `1` werden gelöscht;
- globale Bits `301`, `302` und `303` werden gelöscht;
- globales Bit `300` wird gesetzt;
- Bits `2..299` bleiben unverändert.

Somit gilt exakt

```text
k = 2^300 + 4*n,  0 <= n < 2^298.
```

Der geklampte Skalar ist immer durch `4` teilbar, besitzt immer 301 Bit und
liegt im Intervall

```text
2^300 <= k <= 2^301 - 4.
```

Es bleiben **298 variable Bits**, nicht 299. Bei gleichverteiltem
38-Byte-Input ist `n` gleichverteilt. Sechs Eingabebits haben keinen Einfluss
auf `k`; deshalb besitzen verschiedene rohe Secret-Bytefolgen denselben
geklampten Skalar. Die rohe Secret-Bytefolge ist keine kanonische
Skalarkodierung.

### 6.2 Begründete Sonderablehnung `k = N_t`

Die Twistordnung `N_t=4*q_t` liegt knapp unter `2^301`, erfüllt selbst alle
Clamp-Bitbedingungen und würde jeden Twistpunkt auf den Punkt im Unendlichen
abbilden. Deshalb ist `k=N_t` kein zulässiger privater X301-v1-Skalar.

Die Ablehnung gilt für **jede** der 64 rohen 38-Byte-Folgen, die nach dem
Clamping `N_t` ergeben. Ein importierter Schlüssel führt in `Public`,
`Shared` und der Kernfunktion zu `FAIL`; `KeyGen` zieht in diesem Fall neue
Zufallsbytes.

Eine konkrete rohe Folge, die abgelehnt werden MUSS, ist die
Little-Endian-Darstellung von `N_t`:

```text
5caf05bd7871f4673bd712e08efdb5dddf8ca4ffffffffffffffffffffffffffffffffffff1f
```

Bei gleichverteiltem Secret-Input beträgt die Ablehnungswahrscheinlichkeit
exakt `2^-298`.

## 7. Vollständige 301-Runden-Montgomery-Leiter

Alle Additionen, Subtraktionen und Multiplikationen innerhalb der Schleife
werden modulo `p` ausgeführt. `CSWAP(b,(x,z),(x',z'))` vertauscht beide
Projektivpaare genau dann, wenn `b=1`. In einer produktiven Implementierung
MUSS `CSWAP` konstantzeitig sein.

```text
function Ladder301(k, u):
    require 2^300 <= k <= 2^301-4
    require k mod 4 == 0
    require k != N_t
    require 0 <= u < p

    x1 = u
    (x2,z2) = (1,0)
    (x3,z3) = (u,1)
    swap = 0

    for bit_index from 300 downto 0:
        bit = (k >> bit_index) AND 1
        swap = swap XOR bit
        ((x2,z2),(x3,z3)) = CSWAP(swap,(x2,z2),(x3,z3))
        swap = bit

        A_  = x2 + z2
        AA  = A_^2
        B_  = x2 - z2
        BB  = B_^2
        E_  = AA - BB
        C_  = x3 + z3
        D_  = x3 - z3
        DA  = D_ * A_
        CB  = C_ * B_

        x3 = (DA + CB)^2
        z3 = x1 * (DA - CB)^2
        x2 = AA * BB
        z2 = E_ * (AA + A24_minus*E_)

    ((x2,z2),(x3,z3)) = CSWAP(swap,(x2,z2),(x3,z3))
    return (x2,z2)
```

Die Schleife MUSS immer genau 301 Iterationen ausführen. Sie DARF weder beim
höchsten gesetzten Bit beginnen noch führende Bits überspringen. `B` aus der
Montgomery-Gleichung wird von den x-only-Differentialformeln nicht benötigt;
es bleibt Bestandteil des zugrunde liegenden Kurvenmodells.

## 8. Normative Kernfunktion

```text
function X301(secret, u_encoded):
    k = DecodeScalar(secret)
    if k == FAIL: return FAIL

    u = DecodeU(u_encoded)
    if u == FAIL: return FAIL

    (X,Z) = Ladder301(k,u)

    if Z == 0 mod p: return FAIL

    u_out = X * inverse(Z) mod p
    out = EncodeU(u_out)
    if out == FAIL: return FAIL

    if AllZero(out): return FAIL
    return out
```

`Z=0` bezeichnet den Punkt im Unendlichen und ist immer ein Fehler. Eine
38-Byte-Nullausgabe ist ebenfalls immer ein Fehler, selbst wenn ein
Implementierungsfehler oder ein nicht erwarteter Rechenpfad sie bei `Z!=0`
erzeugen sollte. Es werden niemals partielle oder ersatzweise Ausgabebytes
zurückgegeben.

Eine gehärtete Implementierung SOLLTE die Prüfung, Auswahl eines sicheren
Inversionsoperanden und Ausgabemaskierung so gestalten, dass ein
secret-abhängiger Fehlerpfad nicht vor Abschluss der vollständigen Leiter
beobachtbar wird. Die mathematische API bleibt dennoch `Ausgabe oder FAIL`.

## 9. Öffentliche Schnittstellen

### 9.1 `KeyGen`

```text
function KeyGen(CSPRNG):
    loop:
        secret = CSPRNG.random_bytes(38)
        if len(secret) != 38: return FAIL

        k = DecodeScalar(secret)
        if k == FAIL because k == N_t:
            continue
        if k == FAIL:
            return FAIL

        public = Public(secret)
        if public == FAIL:
            return FAIL              # interner Fehler; bei gültigem k unmöglich
        return (secret, public)
```

Der CSPRNG MUSS 38 gleichverteilte, unabhängige Bytes liefern. Passwort,
Text, Zähler, Zeitstempel oder bereits reduzierte Skalare sind keine
zulässigen Ersatzquellen. `KeyGen` gibt die ursprünglichen rohen 38 Secret-
Bytes zurück; jeder Gebrauch führt das Clamping erneut deterministisch aus.

### 9.2 `Public`

```text
function Public(secret):
    return X301(secret, BASE_U_ENCODED)
```

Für jeden von `DecodeScalar` akzeptierten geheimen Eingang ist `Public`
erfolgreich. Die Ausgabe ist eine kanonische 38-Byte-u-Koordinate eines
Punkts der Haupt-Primuntergruppe.

`Public` prüft nur Form und den ausgeschlossenen Skalar, nicht die Entropie
eines importierten Secrets. Die Sicherheitsgarantie setzt einen durch
`KeyGen` erzeugten Secret-Input voraus.

### 9.3 `Shared`

```text
function Shared(secret, peer_public):
    return X301(secret, peer_public)
```

Sind `(secret_A,public_A)` und `(secret_B,public_B)` jeweils durch `KeyGen`
erzeugt, gilt

```text
Shared(secret_A,public_B) == Shared(secret_B,public_A)
```

und beide Seiten erhalten dieselbe kanonische rohe u-Ausgabe. Ein Fehler auf
einer Seite MUSS den aufrufenden Vorgang abbrechen; der Fehler DARF NICHT
durch Nullbytes, den Eingabewert oder einen anderen Ersatzwert fortgesetzt
werden.

Public Keys und Shared-Ausgaben enthalten ausschließlich die 38 u-Bytes;
ihnen wird kein Suite-, Versions- oder Rollenbyte vorangestellt. Ein äußerer
Parser MUSS `X301-v1` vor dem Aufruf eindeutig ausgewählt haben und DARF eine
fehlgeschlagene Operation nicht versuchsweise unter einem anderen Verfahren
wiederholen.

## 10. Vollständige Fehlerregeln

`X301`, `Public` oder `Shared` liefern `FAIL`, wenn mindestens einer der
folgenden Fälle eintritt:

1. Secret ist keine Bytefolge oder nicht exakt 38 Byte lang.
2. Der geklampte Skalar ist exakt `N_t`.
3. Die u-Eingabe ist keine Bytefolge oder nicht exakt 38 Byte lang.
4. Eines der u-Bits `301..303` ist gesetzt.
5. Der dekodierte u-Integer ist `>=p`.
6. Die Leiter liefert `Z=0`.
7. Die kodierte affine Ausgabe besteht aus 38 Nullbytes.
8. Eine Feldoperation oder interne Konsistenzprüfung schlägt fehl.

`KeyGen` wiederholt ausschließlich Fall 2 mit frischen 38 Zufallsbytes.
Ein CSPRNG- oder interner Fehler beendet `KeyGen` mit `FAIL`. Import-, Public-
und Shared-Operationen wiederholen oder verändern den vom Aufrufer gelieferten
Secret-Input nicht.

Eine Bibliothek DARF intern detaillierte Diagnosen bereitstellen. Ein
Netzwerkprotokoll SOLLTE Dekodier-, Kleinordnungs-, Twist- und
Secret-Sonderfehler nach außen als denselben generischen Handshakefehler
behandeln, sofern sein eigenes Protokolldesign nichts strengeres verlangt.

## 11. Mathematische Konsistenz der Clamp- und Twist-Regel

### 11.1 Cofactor Clearing

Jede kanonische affine u-Koordinate beschreibt die x-Linie der Hauptkurve
oder ihres quadratischen Twists; bei einer Nullstelle der rechten Seite liegt
ein Torsionsfall vor. Beide rationalen Gruppen sind zyklisch und haben Ordnung
`4*Primzahl`.

Da jeder geklampte Skalar durch `4` teilbar ist, annihiliert die
Multiplikation den vollständigen rationalen Cofaktor sowohl auf der
Hauptkurve als auch auf dem Twist. Das Ergebnis liegt, sofern es nicht der
Punkt im Unendlichen ist, in der jeweiligen Primuntergruppe.

### 11.2 Ausschluss weiterer annihilierender Skalare

Die Clamp-Menge ist

```text
S = { 2^300 + 4*n | 0 <= n < 2^298 }.
```

Für die Hauptgruppe gilt `q mod 4 = 3`. Im Clamp-Intervall kommen als
mögliche kleine `q`-Vielfache nur `2q` und `3q` in Betracht:

```text
2q = 2^300 +
     1019698330281105344162687147175522961895271430,
2q mod 4 = 2,
3q mod 4 = 1,
4q = N = 2^301 +
     2039396660562210688325374294351045923790542860.
```

Damit liegt kein durch `4` teilbares `q`-Vielfaches in `S`; `Public` kann für
einen akzeptierten Secret-Input nicht den Punkt im Unendlichen liefern.

Für den Twist gilt `q_t mod 4 = 3`:

```text
2q_t = 2^300 -
       1019698330281105977987987261290223710246873170,
3q_t mod 4 = 1,
4q_t = N_t = 2^301 -
       2039396660562211955975974522580447420493746340.
```

`2q_t` liegt unterhalb der Clamp-Menge, `3q_t` ist nicht durch `4` teilbar,
`4q_t=N_t` wird ausdrücklich verworfen und `5q_t` liegt oberhalb von
`2^301`. Somit enthält die akzeptierte Clamp-Menge auch kein
`q_t`-Vielfaches.

Folglich kann ein akzeptierter Secret-Skalar nur reine Cofaktor-Torsion auf
den Punkt im Unendlichen abbilden. Die verpflichtenden `Z=0`- und
All-zero-Prüfungen erkennen diesen Fall.

### 11.3 Effektive private Auswahlmenge

Vor der Sonderablehnung enthält die Clamp-Menge exakt `2^298` Skalare. Nach
Ablehnung von `N_t` verbleiben `2^298-1` mögliche geklampte Skalare. Die
Abbildung auf die Haupt-Primuntergruppe ist injektiv, denn zwei verschiedene
Clamp-Werte unterscheiden sich um weniger als `2^300`, und aus
`q | 4*(n1-n2)` würde wegen der Primheit und Ungeradheit von `q` bereits
`q | (n1-n2)` folgen, obwohl `|n1-n2|<2^298<q` gilt.

Damit entstehen bei ordnungsgemäßem `KeyGen` praktisch 298 Bit private
Entropie und `2^298-1` verschiedene volle Gruppenpunkte `[k]G`. Die
u-Kodierung identifiziert wie jede Montgomery-x-only-Darstellung `P` und
`-P`; verschiedene volle Punkte können deshalb dieselbe öffentliche
u-Kodierung besitzen. Dieser Vorzeichenquotient ist in der nachfolgenden
generischen Grenze bereits zu berücksichtigen und begründet keine stärkere
Sicherheitsangabe.

Ein generischer Intervallangriff gegen die bekannte Scalar-Menge hat eine
Größenordnung von `2^149` Gruppenoperationen. X301-v1 darf deshalb als rohe
XDH-Funktion mit ungefähr 149 Bit generischer Exponentensicherheit beschrieben
werden, nicht als Funktion mit einer harten 150-Bit-Untergrenze. Die
geringfügig höhere generische DLP-Schätzung der vollen Kurvengruppe hebt die
Begrenzung durch das Secret-Format nicht auf.

## 12. Contributory Behavior und KDF-Grenzen

Die Kombination aus Cofaktor-4-Clamping, bewiesener Twistordnung und
verpflichtender Nullergebnis-Ablehnung verhindert, dass ein akzeptierter
Kleinordnungseingang ein scheinbar verwendbares konstantes Shared-Ergebnis
liefert. Dies ist eine wichtige contributory-behavior-Eigenschaft, aber kein
vollständiger Beweis eines sicheren Handshakes.

Insbesondere garantiert die rohe Funktion nicht:

- Besitz des zum Peer-u-Wert gehörenden geheimen Schlüssels,
- Authentizität oder Identität des Peers,
- Unknown-Key-Share-, Key-Compromise-Impersonation- oder Replay-Schutz,
- Rollen-, Algorithmus-, Versions- oder Transkriptbindung,
- Forward Secrecy bei Wiederverwendung statischer Secrets,
- Gleichverteilung der 38 Rohausgabebytes als symmetrischer Schlüssel.

Die Ausgabe von `Shared` DARF NICHT unmittelbar als Schlüssel, Nonce,
One-Time-Pad oder Authentikator verwendet werden. Ein vollständiges
Anwendungsprotokoll MUSS eine analysierte KDF verwenden und darin mindestens
Algorithmus/Version, Rollen, beide öffentlichen Schlüssel und das relevante
Handshake-Transkript eindeutig binden. Die Wahl einer konkreten KDF und eines
Handshake-Formats liegt ausdrücklich außerhalb von X301-v1.

X301-v1 akzeptiert absichtlich sowohl Hauptkurven- als auch sichere
Twisteingaben, sofern das Ergebnis nicht der Punkt im Unendlichen ist. Eine
erfolgreiche Operation ist daher kein Nachweis, dass der Peer-Wert aus
`Public` oder aus der Haupt-Primuntergruppe stammt. Ein höheres Protokoll, das
diese Eigenschaft benötigt, muss sie separat authentisieren oder validieren.

## 14. Anforderungen an Konformitätsvektoren

Eine vollständige maschinenlesbare X301-v1-Vektorsammlung MUSS mindestens
enthalten:

- Secret-Längen `37`, `38` und `39` Byte;
- Clamp-Grenzen, alle sechs ignorierten/überschriebenen Bits und den Nachweis
  von genau 298 variablen Bits;
- den ausgeschlossenen Skalar `N_t` sowie mehrere seiner rohen Präbilder;
- `Public` für feste Secrets, einschließlich der Vektoren aus Abschnitt 13;
- beidseitige `Shared`-Übereinstimmung für mehrere Schlüsselpaare;
- kanonische Hauptkurven- und Twisteingaben;
- u-Werte der rationalen Cofaktor-Torsion mit erwartetem `FAIL`;
- `u=0`, `u=1`, `u=p-1`, `u=p` und einen Wert oberhalb `p`;
- jede einzeln gesetzte reservierte u-Bitposition `301..303`;
- einen `Z=0`- und einen All-zero-Ablehnungspfad;
- Nachweis, dass genau 301 Leiteriterationen ausgeführt werden;
- Abgleich der Leiter mit allgemeiner Punktmultiplikation auf Hauptkurve und
  Twist, ohne dieselbe Leiter als alleinige Erwartungswertquelle zu verwenden;
- unveränderte Ablehnung bei falscher Algorithmus- oder Versionsauswahl im
  äußeren Parser.

Positive Vektoren MÜSSEN Secret, geklampte Bytes, Integer `k`, Eingabe-u,
projektive Endwerte `(X,Z)`, affine u-Ausgabe und sämtliche 38-Byte-Kodierungen
enthalten. Negative Vektoren MÜSSEN die genaue Ablehnungsstufe dokumentieren,
ohne diese Detailstufe zwingend über eine Netzwerk-API offenzulegen.

## 15. Anforderungen an Implementierungen

Eine Implementierung, die Produktionsnähe beansprucht, MUSS zusätzlich zur
funktionalen Konformität mindestens erfüllen:

- konstante 301-Runden-Ausführung unabhängig vom Secret;
- konstantzeitliches `CSWAP` und keine secret-indizierten Speicherzugriffe;
- konstantzeitliche Feldarithmetik, Inversion, Scalar-Sonderprüfung und
  All-zero-Prüfung;
- keine Ausgabe partieller Zwischenergebnisse bei `FAIL`;
- sichere Löschung von geklampften Skalaren und Feldzwischenwerten, soweit
  Plattform und Sprache dies ermöglichen;
- CSPRNG-Fehlererkennung und korrektes Neu-Ziehen ausschließlich für
  `k=N_t`;
- strikte Längen-, High-bit- und `u<p`-Prüfung vor der Leiter;
- Cross-Tests gegen mindestens eine unabhängig geschriebene Implementierung;
- Tests auf Timing-, Cache-, Fault- und Invalid-Input-Verhalten.

Eine variable-time Big-Integer- oder affine Auditimplementierung kann
Konformitätswerte reproduzieren, DARF aber nicht als produktionsgeeignet
bezeichnet werden. Auch eine konstante Leiter allein genügt nicht, wenn
Feldinversion, Fehlerbehandlung oder Speicherzugriffe Secret-Informationen
preisgeben.

## 16. Zulässige Sicherheitsbeschreibung

Eine korrekte Kurzbeschreibung lautet:

> X301-v1 is a strictly encoded raw Montgomery XDH function over ED301-v1.
> Its clamped secrets contain 298 variable bits, its accepted inputs are
> protected by the proven cofactor-4 main-curve and twist structure, and
> zero/infinity results are mandatory failures. It provides roughly 149-bit
> generic private-exponent security. It is not a KDF, an authenticated
> handshake, or a production-audited implementation.

Stärkere Aussagen – insbesondere „mindestens 150 Bit“, „authentisierter
Schlüsselaustausch“, „direkt als Sitzungsschlüssel verwendbar“ oder
„vollständiges contributory behavior für beliebige Protokolle“ – sind durch
diese Spezifikation nicht gedeckt.
