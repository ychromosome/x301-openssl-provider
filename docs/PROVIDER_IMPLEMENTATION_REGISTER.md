## X301 provider additions

Date: 2026-08-25. Sources: OpenSSL 3.5.8/4.0.2 provider contracts, FIPS 203,
RFC 9846, and RFC 10024.

| Area | Required implementation | Why it exists | Replacement or deletion trigger | Required permanent evidence |
| --- | --- | --- | --- | --- |
| X301 KEYMGMT/KEYEXCH | Add a distinct X301 key type and 38-byte derive surface by sharing existing provider context, fixed-length import/export, error and secret-owner patterns. | OpenSSL KEYEXCH is the requested direct X301 API. Key-type separation enforces H5 at the EVP-object boundary. | Delete copied infrastructure; retain only X301-specific dispatch and lengths. | T6/T7 in both lanes, cross-type Ed301/X301 negatives, lifecycle and zeroization tests. |
| X301MLKEM1024 libssl adapter | Expose the KEYMGMT/KEM operations named by a `TLS-GROUP` capability with `is-kem=1`; they are technically fetchable by ordinary EVP because that is how libssl invokes the group. | Mandatory OpenSSL architecture, not a promise of a standalone hybrid-KEM protocol. | Delete any non-TLS OID, persistence, KDF, codec or application profile. If OpenSSL later offers a smaller standard TLS-only contract, reassess and prefer it. | EVP fetch/dispatch test plus T8/T9 in both exact lanes. |
| ML-KEM-1024 component | Fetch ML-KEM-1024 through EVP in the provider child library context with a null local property query, so the context's configured properties select the implementation. | E1: FIPS 203 cryptography remains OpenSSL-owned without hard-coding one provider name. | Any project-owned ML-KEM symbol, crate, vendored code or copied substep is a removal finding. | Selected-provider inspection, default-present integration KAT and unavailable-implementation failure in both lanes. |
| Hybrid layout | Parse and emit exactly 1568-byte ML-KEM component followed by 38-byte X301 component; concatenate 32-byte ML-KEM secret followed by 38-byte X301 secret. | RFC 9954 ordered-component convention and RFC 10024's ML-KEM-first bytes. | Delete alternate ordering, length inference and any hash/KDF. | H2 +/-1 boundary matrix and 1606/1606/70 assertions. |
| Random generation | Route X301 key generation through one provider-owned `EVP_RAND_CTX` (`CTR-DRBG`, fetched under the child-context policy, no parent, locking enabled, created on first use, uninstantiated and freed in teardown); let the fetched OpenSSL ML-KEM implementation use its standard RNG path. Derive/decaps with fixed keys must not call X301 RAND. | E4 and the existing poisoned-RAND assurance pattern; the same seeding route (core `get_user_entropy`) that OpenSSL's own providers use for their DRBGs. | Delete any hybrid or X301-specific RNG abstraction beyond this single instance. | T7 poisoned-RAND split, fail-closed-without-permitted-DRBG and provider-reload tests, complete handshake. |
| Hybrid secrets and failures | Reuse existing fallible allocation, no-partial-output, zeroization and drop ownership. Preserve OpenSSL ML-KEM implicit rejection verbatim. | H3/T13 without a parallel secret lifecycle. | Delete copied owners or code that detects/rewrites an implicit-rejection secret. | T9, allocation failures, taint, drop/zeroization and protected-record authentication failure after a wire mutation. |
| Nested EVP use | Use the provider child `OSSL_LIB_CTX` for ML-KEM fetches and inherit its provider/property policy. Capability discovery stays side-effect free; if no permitted ML-KEM implementation exists, hybrid key generation/import fails cleanly. | External providers must not cast the core context; ML-KEM must remain OpenSSL-owned and composable with application policy. | Prefer a smaller standard core upcall if OpenSSL later provides one. Do not add a parallel RNG or auto-load policy. | Selected-provider inspection and isolated ML-KEM-unavailable failure test. |
| Child-context thread lifecycle | No per-thread state is created on the child `OSSL_LIB_CTX`: X301 randomness comes from the provider-owned DRBG above, ML-KEM randomness from the application context (child providers share the parent provider context). Temporary nested EVP contexts are freed before return; refcounted returned `EVP_PKEY` objects remain live. No `OPENSSL_thread_stop_ex(child)` is issued. | `RAND_priv_bytes_ex(child)` registers, per thread, a thread-exit handler that dereferences the child context, and OpenSSL frees a context with only the calling thread's handlers (OPENSSL_init_crypto(3)). The former per-operation thread stop mitigated that at a measured 4x keygen throughput loss at 16 threads. | Revisit if the provider ever creates thread-local state on the child context again. | Cross-thread teardown regressions in the raw and hybrid harnesses perform OpenSSL's required worker-side stop for the application-owned host context, then outlive provider and host context; Valgrind independently detects any stale provider-child handler (negative control: removing the stops without this DRBG change fails with an invalid read in `rand_delete_thread_state`). Repeated returned-key use and dual-lane TLS are also required. |

Replacements MUST retain fallible allocation, secret cleanup, ordinary/test
artifact separation, and both OpenSSL-lane lifecycle and taint gates.
